## Product fit and implementation order

1. **Payments:** Stripe-hosted Checkout and customer portal for purchases; never collect raw card details on the website.
2. **Billing:** Build three recurring subscription Products/Prices; associate each subscription with an authenticated local account and immutable Stripe customer ID.
3. **Tax:** Confirm business entity, locations, tax registrations and correct tax code for digital SaaS; consider Stripe Tax automatic tax. Tax calculation is not a substitute for legal registration or filing.
4. **Connect:** Defer. Stripe Connect is for moving money to third-party sellers or creators; not required for first-party SaaS subscriptions. Add it only if a third-party marketplace/payout model is approved.

## Architecture

- Frontend: GitHub Pages; public assets and publishable configuration only.
- API: Cloudflare Worker (or another trusted server) with allowed origin and request validation.
- Auth: Managed authentication with verified user ID. Keep account email/provider mapping server side.
- Data: Database tables `users`, `stripe_customers`, `subscriptions`, `campaign_usage`, `campaigns`, `webhook_events`.
- Billing: Stripe Checkout Session created server-side with `mode=subscription`, a price ID selected from the server's allowlist, and a Stripe Customer ID belonging to the authenticated user.
- Lifecycle: Validate signed Stripe webhooks with raw request body; store processed event IDs for idempotency; reconcile with current Stripe subscription state for out-of-order delivery.
- Entitlements: Backend checks user authorization, Stripe subscription status, period and usage counters; DB transaction/reservation prevents quota races. Only then generate and save the requested campaign on the backend.
- Billing management: Portal sessions created server-side for the authenticated user's existing Stripe Customer ID.
- Tax: Compute taxes via Stripe Tax if enabled/appropriate, collect location details, and verify registration obligations before live-mode launch.
- No Stripe secret, webhook signing secret, AI API secret, or service-role database credentials may be published in GitHub Pages, localStorage or chat.

## API sketch

- POST /api/billing/checkout — authenticated; accepts only plan enum; returns Stripe-hosted checkout URL.
- POST /api/billing/portal — authenticated; returns customer portal URL.
- POST /api/webhooks/stripe — raw body, signature verification, idempotent event handling.
- GET /api/me/entitlements — authenticated; returns plan and remaining server-side quota.
- POST /api/campaigns — authenticated; validates quota; creates campaign; reserves an operation safely.
- GET /api/campaigns — authenticated; only user's own campaigns.

## Core webhooks

- checkout.session.completed — associate Checkout Customer/Subscription to local account, don't grant premium without validated subscription state.
- customer.subscription.created/updated/deleted — synchronize entitlements and plan lifecycle.
- invoice.paid — paid renewal / billing record, if appropriate.
- invoice.payment_failed — record payment issues; apply a documented grace-policy.
- payment disputes/refunds if one-time purchases are later added.

Do not assume webhook order. Use Stripe API to reconcile uncertain states.

## Subscription policy to decide before launch

- Billing currency and monthly prices, included credits, and renewal dates.
- Start/stop policy: cancellation end-of-period vs immediate.
- Upgrade proration, downgrade, failed payment grace period.
- Monthly counters: subscription-period usage vs calendar-month.
- Trial/refund rules; support contact; recurring-charge disclosure.
- Tax registration/jurisdictions and correct product tax code.
- Whether old one-time campaign purchase is discontinued or remains as an optional SKU.
- What “AI campaign” truly includes; current v4 generator is rule-based and must not be advertised as live AI.

## Verification tests (Stripe test mode)

1. Successful Starter checkout followed by valid webhook -> authenticated access.
2. Unpaid/failed checkout -> no premium access.
3. Checkout redirect without validated subscription -> no access.
4. Duplicate/out-of-order webhook events -> idempotent state.
5. Cross-account customer or campaign ID -> rejected.
6. Quota zero -> no generation; concurrent double-spend -> prevented.
7. Upgrade/downgrade, renewal, cancellation, delinquency and portal transitions.
8. Tax behavior by test customer location; compliant receipts, customer notices.
9. Key rotation and webhook endpoint signing secret rotation.
10. No real charges until explicit live-mode approval.
